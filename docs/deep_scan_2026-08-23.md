## Critical — security

### 1. Rate limiting is bypassable everywhere it's applied
`backend/rate_limit.py:19-32` keys every `@limiter.limit()` decorator on the
client-supplied `X-Contributor-Id` header, which `backend/contributor.py` only
validates for UUID *shape* — not identity. Any caller can mint a fresh random
UUID per request and land in a fresh rate-limit bucket every time, fully
defeating the limit. This isn't one bug, it's the root cause behind four
separate real exposures:
- `POST /api/admin/login` (`admin_auth.py:47`, nominally `10/minute`) — the
  admin password (`REVIEWER_API_KEY`, bcrypt-hashed) can be brute-forced at
  unlimited speed with no account lockout.
- `POST /api/generate-image` / `/api/generate-video` (`image.py:86,92`,
  nominally `5/minute`) — unbounded calls against paid Gemini Imagen quota.
- `/api/chat`, `/api/document` — same mechanism, unbounded calls against the
  Cerebras/Groq/Gemini fallback chain's paid quota.
- `POST /api/analytics/visit` (public beacon, `60/minute`) — combined with
  finding #13 below, an unbounded row-insertion vector.
- Also, independent of abuse: the in-process bucket dict has no eviction, so
  a sustained rotating-UUID attack grows server memory without bound.

**Fix direction:** rate-limit on IP address as the primary key (SlowAPI
supports this natively via `get_remote_address`), with `X-Contributor-Id`
only as a secondary/fairness signal, not the sole key.

### 2. `/api/live` and `/api/tts` bypass the optional API key entirely
`backend/main.py:185` registers `audio.router` without `dependencies=_auth`,
while every other product router (chat, image, feedback, document,
dictionary) has it. `main.py`'s own docstring states the API key, when set,
gates "every request." If an operator sets `API_KEY` expecting a private
deployment, the two most compute-expensive endpoints — live voice (STT→LLM→TTS)
and TTS synthesis — stay fully open regardless, reachable from any website's
JS via an unauthenticated WebSocket (WebSocket handshakes aren't subject to
CORS at all).

**Fix direction:** add `dependencies=_auth` to `audio.router`'s registration,
or document explicitly why it's intentionally exempt (like `waxal`/`analytics`
already do in nearby comments).

### 3. Admin pronunciation endpoints are CSRF-able
`backend/routers/pronunciation.py:154` (`POST /api/admin/pronunciation` and
`.../record`) accept `multipart/form-data` — a CORS "simple" content type that
triggers no preflight — and are gated only by a `SameSite=None; Secure`
session cookie (`admin_auth.py:36-44`, deliberately `None` so the cookie works
across `app.murya.ng`/the API domain) with no CSRF token and no `Origin`
check. A malicious page with an auto-submitting form, visited by a
logged-in admin within their 12h session, can silently create a
pre-"approved" pronunciation recording that then gets served to real users
as the highest-priority TTS override.

**Fix direction:** add a CSRF token to admin state-changing requests, or at
minimum validate `Origin`/`Referer` on these two routes.

### 4. Nested `pow()` bypasses the calculator's DoS guard
`backend/services/calc_service.py:95` — live-tested during this scan:
`(2**999)**999` (base already computed from a prior *allowed* exponentiation)
passes the guard since only the immediate exponent is checked. A 3-level
chain, `((2**999)**999)**999`, took 7.46s and built a ~125MB integer with no
error. `calc_service.calculate()` is reached directly from unauthenticated
chat text via `chat.py`'s math-detection path — a short, innocuous-looking
message can hang/OOM a worker.

**Fix direction:** track the bit-length of intermediate results through the
whole expression tree, not just literal exponents.

## Critical — correctness

### 5. Chat's fallback chain can splice two different providers' output into one reply, then cache it
`backend/routers/chat.py:909-981` — `full_text` accumulates every token
pulled off the queue regardless of which provider produced it. If a provider
raises *after* already streaming several tokens (network blip, quota cutoff
mid-generation), the `except` block starts the next provider from scratch —
but the already-queued tokens from the first provider are never discarded.
The client receives one `isDone:true` response whose text is a garbled
concatenation of two unrelated answers, presented as a normal success. Worse:
since `full_text` is non-empty, it gets written into `_CHAT_CACHE`
(`chat.py:976-980`) and replayed verbatim to a *different* user asking the
same cacheable question later. The same pattern exists one level deeper in
`stream_gemini`'s grounded-search retry (`chat.py:805-822`).

**Fix direction:** reset the accumulator (not just track a separate
per-provider buffer) on every fallback transition, and only cache output
from a provider that completed cleanly.

### 6. A provider returning zero tokens looks like a successful reply
`backend/routers/chat.py:700-706` (`stream_ollama`) catches
`StopAsyncIteration` on the first chunk and returns cleanly — no exception,
so the fallback-triggering `except` never fires. The same gap exists
implicitly for every provider (`if delta:`/`if chunk.text:` guards mean an
all-empty stream produces zero output but also zero errors). The request
finishes with `isDone:true` and an empty or partial reply instead of falling
through to the next provider. `backend/routers/document.py:87-105` has the
identical bug — an empty stream reaches `break` immediately and ships
`{"text": "", "isDone": true}` for a translate/summarize request, skipping
the rest of the chain entirely.

**Fix direction:** explicitly track "did this provider yield any real
content" and treat zero-content as a failure that continues the fallback
chain.

### 7. Hooked-consonant words lose capitalization at sentence start
`backend/orthography.py:60-70` (`normalize_hausa_orthography`) — the
case-insensitive regex branches (`\bb'`, `\bd'`, `\bk'`, `'y`, `ts'`, all
`re.IGNORECASE`) run *before* the case-sensitive uppercase branches and
consume the match first, so the uppercase branches are dead code. Input
`"B'aure ne sunan garin."` (sentence starting with a capitalized ɓ-word)
normalizes to `"ɓaure..."` instead of `"Ɓaure..."` — silently lowercasing
what should be a capital letter, for every ɓ/ɗ/ƙ/'y/ts word at a sentence or
proper-noun start. This function is called on every displayed message and
every TTS input (`chat.py:855/857/894/992`, `audio.py:976`).

**Fix direction:** run the case-sensitive (uppercase) branches first, or
merge into one regex with a case-preserving replacement function.

### 8. Live voice: hanging up never releases the microphone
`App.tsx:207-321` — the `MediaStream`, `MediaStreamAudioSourceNode`, and
`ScriptProcessorNode` created in `onopen` are only closure-local variables,
never stored in a ref. Hangup, `onclose`, and `onerror` all update UI state
but never call `stream.getTracks().forEach(t => t.stop())` or disconnect the
processor — the browser's mic-in-use indicator stays lit indefinitely after
hangup (a real privacy issue for a voice product), and because
`audioContextsRef.current.in` is reused across calls, redialing attaches a
*second* `onaudioprocess` handler while the orphaned first one keeps firing
into the new session — a real risk of garbled/doubled audio on any
call-hangup-redial sequence.

**Fix direction:** store `stream`/`scriptProcessor` in a ref, add explicit
teardown in all three exit paths (hangup, close, error).

## High

### 9. PCM16 encoding overflows on full-scale audio
`utils/audio.ts:99` — `int16[i] = data[i] * 32768` should be `* 32767`. A
Float32 sample of exactly `1.0` (common after clipping/AGC) becomes `32768`,
overflowing `Int16Array`'s range and wrapping to `-32768` — inverted-polarity
distortion sent to STT on every live-voice mic frame that happens to hit
full scale, i.e. the loudest, most important parts of speech.

### 10. TTS mangles phone numbers and codes with leading zeros
`backend/orthography.py:123-159` (`hausa_cardinal`/`_spell_number_token`)
routes numeric tokens through `int()` before spelling them out, silently
dropping leading zeros. A phone number like `"08012345678"` becomes
`int(...)` = `8012345678` (10 digits, first digit gone) and is read back
missing a digit; `"0500"` gets read as "five hundred" instead of
digit-by-digit "zero five zero zero" — changing what the number actually
means when spoken aloud by the assistant.

### 11. Dictionary silently drops real single-letter headwords
`backend/services/dictionary_service.py:151` (`_is_noise`) treats every
single alphabetic character as OCR/grammar-tag noise. A real Hausa
preposition or English article that happens to be exactly one letter (e.g.
Hausa "a") is unconditionally discarded during load — `define("a")` returns
nothing even if the source lexicon genuinely defines it.

### 12. A `speaker_id` typo silently searches the wrong-gender voice bank
`backend/routers/waxal.py:185-189` — if a supplied `speaker_id` matches zero
samples, the code falls back to searching the *entire unfiltered* dataset
instead of erroring, potentially matching and returning a recording from the
wrong gender/voice — exactly the failure mode a comment elsewhere in
`audio.py` explicitly warns about, but unguarded here.

### 13. Analytics table has no retention policy
`backend/analytics_store.py` — the `visits` table has no pruning/row-cap
logic anywhere; every page load is inserted forever. Combined with finding
#1 (the beacon's rate limit is bypassable), this is an unbounded growth
vector on the single Fly/Azure volume, and `summary()`'s aggregate queries
scan the whole table regardless of the requested date window, so they get
slower over time with no code path to reverse it.

### 14. Admin review-queue actions fail silently
Across `CorrectionsReview.tsx`, `QAReview.tsx`, and
`PronunciationReview.tsx`: approve/reject/delete calls don't check their
own success/failure before refreshing the list, and don't disable the
button they're bound to. A failed approve just leaves the item sitting in
"pending" with zero indication anything went wrong, and rapid double-clicks
can fire two concurrent requests for the same row. `PronunciationReview.tsx`
additionally shares one recorder instance (`flagRec`) across every row —
starting a second row's flag-recording silently abandons the first's live
mic stream (leaked, never stopped).

### 15. `_transcribe_via_cloudflare` / search / You.com services can raise past their own "never raises" contract
`cloudflare_stt_service.py:96`, `search_service.py:82`, `you_service.py:64`
all call `.get(...)` on the parsed JSON response *outside* the try/except
that produced it. A non-dict JSON body on any edge-case response (a bare
`null`, an array) raises `AttributeError` straight into the request path,
contradicting each module's own documented "never raises" contract.

## Medium

- **Chat/document providers instantiate a fresh SDK client per request**
  (`chat.py:627,664,693,733,783`) with no reuse/teardown — a slow connection-pool
  leak under sustained traffic.
- **Corrections file is read + parsed synchronously on every chat/audio
  request** (`corrections_store.py:38-47`, called from `chat.py:564,776`,
  `audio.py:188`), blocking the single asyncio event loop for the duration —
  gets worse as the corrections log grows, with no cap on how many corrections
  get folded into the system prompt either.
- **`corrections_store.py`** has no try/except around `json.loads` in
  `_read_all`, and downstream code uses direct dict subscript (`e["id"]`)
  instead of `.get()` — one malformed line or one incomplete-but-valid-JSON
  record takes down `get_approved_corrections_prompt()`, which every single
  chat/audio request calls unconditionally with no fallback.
- **Dictionary's first load blocks the event loop** — `dictionary_service.py`'s
  `_load()` synchronously parses up to three JSONL files (~30,700 entries)
  inline on the first request that needs it, no `run_in_executor`.
- **`waxal.py`'s metadata file is re-parsed from scratch on every single TTS
  call** (`audio.py:248-291`, `_find_closest_waxal_sample`) — no caching, and
  per finding #12's related bug, this runs on effectively every TTS request
  since `speaker_id: int = 0` (not `None`) makes the "explicit selection"
  gate always true.
- **VITS engine re-attempts full ONNX session init on every call after a
  first failure** (`vits_engine.py:205`) instead of caching the failure —
  every TTS request pays the full expensive init cost while the model is
  broken.
- **Piper model download has no concurrency lock**
  (`audio.py:199-217,348-371`) — two simultaneous first-TTS-requests after a
  fresh deploy can both write to the same model file path concurrently,
  risking a corrupted model.
- **`generate_video` leaks the imageio/ffmpeg writer on a mid-loop failure**
  (`image.py:136-139`) and **leaks raw exception text to the client** on
  failure (`image.py:150-152`, unlike the sibling image-gen path which
  returns a generic message).
- **Image/video prompts accept blank/whitespace-only input**
  (`image.py:32-38`) — a billed Gemini call runs for a functionally empty
  prompt with no validation.
- **`main.py`'s CORS validation misses the empty-string case** — setting
  `ALLOWED_ORIGINS=""` in production passes startup validation but silently
  configures `allow_origins=[]`, blocking all cross-origin traffic while
  `/health` still reports fine.
- **`CORSMiddleware` isn't outermost** — a genuinely unhandled exception
  (not caught by any route) produces a 500 with no CORS headers at all,
  which browsers report as an opaque network failure rather than a real
  error.
- **Startup model preload swallows all exceptions** (`main.py:104-141`) —
  a broken/missing VITS model at boot logs a warning only; `/health` reports
  healthy regardless, with no way to distinguish "degraded" from "broken"
  short of an actual TTS request failing.
- **Frontend: send isn't gated on `isLoading`** — `InputConsole.tsx`'s send
  button/Enter handler and the live-voice mic button don't check `isLoading`,
  letting a user fire overlapping concurrent chat streams.
- **`DictionarySearch.tsx`'s debounced search has no stale-response guard**
  — an out-of-order network response can silently overwrite newer, correct
  results with older ones (the codebase already has the right pattern for
  this in `DocumentTool.tsx`'s `runId` ref, just not applied here).
- **`learningService.ts`'s singleton constructor has no try/catch around
  `JSON.parse`** — corrupted localStorage can throw at module-import time,
  before `App.tsx` even renders, white-screening the whole app.
- **Live-voice `toneMapped` field-name mismatch** — `localService.ts`
  already renames the field to camelCase before `App.tsx` reads it back
  under the old snake_case name, so the tonal-melody trace is always empty
  for live-voice turns specifically (text chat does this correctly).

## Low / informational

- `HOOKED_MAP` in `orthography.py` is defined but never referenced —
  `normalize_hausa_orthography` re-implements the same mapping by hand, two
  sources of truth that can drift.
- `prayer_service.py`'s city label defaults to "Kano" when coordinates are
  supplied without an explicit city string (not currently reachable from
  `chat.py`, but a latent trap for any future caller).
- Several places swallow promise rejections with no user feedback:
  `handlePlaySpeech`'s `audio.play()`, `NeuralReview.tsx`'s audio playback,
  file-upload `FileReader` with no `onerror`, clipboard copy in
  `DocumentTool.tsx`.
- `Date.now().toString()` used as a React key for live-voice transcript
  messages — two messages landing in the same millisecond would collide.
- `GroundingNode.tsx` calls `.includes()` on `source.uri` with no null
  check against an unvalidated backend field.
- `Waveform.tsx` has an off-by-one center index in its 40-bar visualizer
  (true center is 19.5, code uses 20) — cosmetic asymmetry only.
- `NeuralReview.tsx`/`AdminPanel.tsx` and `VisitorAnalytics.tsx`/
  `NeuralReview.tsx` each independently reimplement the same
  fetch-and-render logic in two places with no shared source of truth —
  not a bug today, but a real drift risk on the next schema change.
- `resampleLinear` in `utils/audio.ts` produces `NaN` instead of an empty
  array on zero-length input (an edge case, not observed in practice).
- Four independent SQLite `init_db()` calls at startup with no cross-process
  locking — only a risk if the deployment ever runs multiple worker
  processes against the same volume, which it doesn't currently.

## Suggested next steps

Given the volume, worth tackling in this rough order: **#1/#2 (auth/rate-limit
gaps)** and **#5/#6 (fallback-chain correctness — this one silently degrades
answer quality and pollutes the cache, so it's a real product-quality bug,
not just an edge case)** first, since those affect every user today. #3/#4
are real but need a deliberate exploit window to matter. #7/#8/#9 are small,
contained fixes with outsized correctness impact given how central
Hausa orthography and live voice are to Murya's actual mission. Everything
under Medium/Low is genuinely worth doing but not urgent.
